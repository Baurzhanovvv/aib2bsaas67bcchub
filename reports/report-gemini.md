#### D-002 — критичное, Противоречие

- Требования: R-011, R-012, R-016, R-017
- Свойство: согласованность набора; пункт стандарта: ISO/IEC/IEEE 29148:2018, 5.2.6 (Consistent)
- Цитаты:

> Сохранение порога
>
> — строка 103

> чтение порога
>
> — строка 103

> | REST type | GET |
>
> — строка 104

> | Request URL | Dev: /alerts/saveLimit . Prod: — |
>
> — строка 108

Почему это дефект: В описании метода одновременно указаны противоположные операции: сохранение порога и чтение порога. Метод HTTP GET указан для операции изменения/сохранения данных, что противоречит спецификации REST (GET не должен изменять состояние ресурса). Для эндпоинта /alerts/saveLimit, изменяющего настройки порога, указан HTTP-метод GET. Для эндпоинта сохранения параметров `/alerts/saveLimit` указан HTTP-метод GET.

Предложение правки: Вопрос заказчику: каким методом выполняется операция? Варианты: 1) POST, PUT или PATCH с параметрами в теле; 2) операция только читает — тогда исправить описание и имя метода.

## 4. Проверка набора требований

#### D-001 — блокирующее, Противоречие

- Требования: R-002, R-009
- Свойство: согласованность набора; пункт стандарта: ISO/IEC/IEEE 29148:2018, 5.2.6 (Consistent)
- Цитаты:

> Месяц определяется по дате совершения покупки в Алматы.
>
> — строка 38

> | Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик вырос на 4 000 ₸ |
>
> — строка 64

Почему это дефект: По правилу R-002 месяц определяется по дате совершения покупки (31 января), то есть сумма должна увеличивать январский счётчик, а критерий R-009 ожидает увеличение февральского счётчика.

#### D-003 — критичное, Пропущенное требование

- Требования: R-011
- Свойство: полнота набора; пункт стандарта: ISO/IEC/IEEE 29148:2018, 5.2.6 (Complete)
- Цитаты:

> Сохранение порога. Функциональные требования: чтение порога
>
> — строка 103

Почему это дефект: В поле описания метода упоминается чтение порога, однако спецификация REST API содержит только эндпоинт сохранения `/alerts/saveLimit` и не содержит описания метода для чтения текущих настроек пользователя. В результате разработчики мобильного приложения не смогут реализовать отображение текущего порога и статуса уведомления при открытии экрана.

#### D-004 — критичное, Некорректное описание интерфейса

- Требования: R-023, R-032, R-036
- Свойство: корректность; пункт стандарта: ISO/IEC/IEEE 29148:2018, 5.2.5 (Correct)
- Цитаты:

> {"result":"ERROR","message":"Проверьте сумму"}
>
> — строка 171

Почему это дефект: В примере ответа для статуса HTTP 200 OK возвращается бизнес-ошибка c result: ERROR. Возврат ошибок под кодом успешного ответа 200 усложняет обработку ошибок на стороне клиента.

Предложение правки: Вопрос заказчику: каким кодом отвечать на ошибку? Варианты: 1) кодом 4xx по причине ошибки; 2) кодом успеха с признаком ошибки в теле — тогда описать это правило явно и убрать расхождение с перечнем статусов.

> 403. Ответ в случае, если на указанный ресурс доступ запрещен.
>
> — строка 175
