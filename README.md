# reqcheck — агент проверки требований

ИИ-агент статической проверки документа с требованиями. Выделяет требования, проверяет каждое и набор
целиком по ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6) и IEEE 830-1998 (п. 4.3) и пишет отчёт на русском:
паспорт прогона, реестр требований, проверка каждого требования, проверка набора, сводка, итог.

Хакатон BCC-HUB × MNU FinTech.

## Быстрый старт

```bash
uv sync                                   # Python 3.11+ uv поставит сам
cp .env.example .env                      # впишите ключ, см. ниже
uv run reqcheck путь/к/requirements.md reports/report.md
```

Первый аргумент — проверяемый документ: Markdown, DOCX или PDF с текстовым слоем. В репозитории его
нет: по условиям хакатона выданный документ сдаётся рядом со ссылкой, а не внутри репозитория. Отчёт
ляжет в файл из второго аргумента, папка создаётся сама. `reports/report.md` в репозитории — отчёт
агента по выданному документу (модель и версия — в его паспорте).

Формат отчёта выбирается расширением файла: `.md`, `.html` (один файл, цитаты подсвечены) или `.pdf`.
Ход работы по этапам печатается в stderr, `--quiet` его отключает. Ответы модели кэшируются в
`.reqcheck_cache`: прерванный прогон при повторном запуске продолжается с того же места и не платит
за уже полученные ответы.

```bash
uv run reqcheck требования.docx отчёт.html
uv run reqcheck требования.md отчёт.pdf --profile bank   # плюс банковские проверки
```

`--profile bank` включает профиль домена: модель дополнительно проверяет, заданы ли валюта и округление
сумм, часовой пояс и границы расчётного периода, повторная доставка события, отмены и возвраты, поведение
на границе лимита, маскирование данных карты, аудит настроек. Без флага профиль не действует.

| Код выхода | Значение |
|---|---|
| 0 | отчёт создан, итог «можно начинать», «можно с условием» или «итог не определён» (проверка неполная) |
| 1 | отчёт создан, итог «начинать нельзя» |
| 2 | отчёт не создан: плохой вход (пустой, скан без текста, не тот формат) |

Нужен [uv](https://docs.astral.sh/uv/).

## Ключ и модель

**Бесплатно — Gemini.** Ключ: <https://aistudio.google.com/> → **Get API key**. Впишите в `.env`:

```
GEMINI_API_KEY=ваш_ключ
```

По умолчанию агент идёт по цепочке бесплатных моделей `gemini-3.1-flash-lite → gemini-3.5-flash-lite →
gemini-3.8-flash`: если у модели кончилась дневная квота или она перегружена, берётся следующая. Свой
список — `REQCHECK_MODEL` через запятую.

**Точнее — Claude (платно).** Лучшие результаты (таблица ниже) получены на `claude-opus-5-5`:

```
REQCHECK_PROVIDER=anthropic
ANTHROPIC_API_KEY=ваш_ключ
REQCHECK_MAX_COST_USD=1.5        # предохранитель: прогон обрывается при превышении
```

Полный прогон на документе ~200 строк — 8 запросов, $0.6–0.8, около 3 минут. Дешевле —
`REQCHECK_MODEL=claude-sonnet-5-5` ($0.31) или `claude-haiku-5-5` ($0.03): итог тот же, шума больше. Стоимость фактического прогона
пишется в паспорт отчёта.

Без ключа (или с `--no-llm`) агент работает только правилами. Правила находят расхождения в описании
API, видные по структуре документа: GET у изменяющей операции, ошибка под кодом успеха, код с чужой
подписью, код вне перечня статусов, разные типы поля в запросе и ответе, путь, которого нет в
OpenAPI-блоке. Смысловые противоречия бизнес-правил без модели не ищутся, поэтому итог такого прогона —
«итог не определён: проверка неполная», а не «можно начинать». То же, если модель отказала посреди
прогона (квота, сеть): отчёт выпускается с причиной сбоя в паспорте.

Файл `.env` в репозиторий не попадает. Все переменные — в `.env.example`.

## Точность

Как мерили: независимый оценщик (не автор промптов) сверял отчёты с предварительным анализом
выданного ТЗ из материалов хакатона — 13 ожидаемых дефектов — и классифицировал каждое замечание:
верно, дубль, придирка, ложно. Пункт засчитан, только если дефект назван словами, а не просто
процитирована строка. Цитаты проверялись поиском по исходному файлу.

Один и тот же агент на трёх моделях и без модели:

| Модель | Найдено из 13 | Точность | Оба ключевых противоречия — блокеры | Итог | Цена | Время |
|---|---|---|---|---|---|---|
| без модели (только правила) | 46% | — | нет | итог не определён | $0 | 1 с |
| `claude-haiku-5-5` | 73% | 73% | да | начинать нельзя | $0.03 | 156 с |
| `claude-sonnet-5-5` | 81% | 74% | да | начинать нельзя | $0.31 | 74 с |
| `claude-opus-5-5` | 81% | **88%** | да | начинать нельзя | $0.63 | 158 с |

- Цитаты: 30 из 30 проверенных дословны и с верным номером строки, в том числе из блоков кода.
- Ложное замечание одно на три отчёта (у Sonnet); остальной шум — дубли и придирки к незаполненным
  блокам шаблона.
- Итог одинаков на всех трёх моделях: серьёзность и итог ставит код, а не модель.
- `reports/report.md` — отчёт из строки `claude-opus-5-5`.

Разброс между прогонами есть: у `claude-opus-5-5` в трёх замерах подряд полнота была 81–92%, точность
84–89%. Строка «без модели» — счёт eval-команды по золотому набору (ниже), остальные — оценщика.

Вклад агента отдельно от силы модели мерили на предыдущей версии (`eval/baseline.py`: тот же документ
и модель, один запрос «найди дефекты»): полнота 88% у голой модели против 85% у агента, точность 80%
против 94%, цитаты с номером строки и итог — только у агента.

На постороннем документе (спецификация API записи на исследование, 341 строка, с нашим ТЗ не связан)
тот же агент на `claude-opus-5-5` дал 21 замечание, из них верных 16, дублей 3, придирок 2, ложных 0;
оценщик назвал пять дефектов, которые агент пропустил. Сам документ в репозиторий не включён.

Оценка — на двух документах, выборка мала: это замер, а не гарантия.

## Что это даёт аналитику

Агент делает первичное ревью документа до того, как его читают люди. На выданном документе (~200 строк)
прогон занял меньше 3 минут и $0.63 на `claude-opus-5-5` — цифры из паспорта `reports/report.md`.

- **Проверять, а не искать.** У каждого замечания дословная цитата и номер строки: аналитик открывает
  место в документе и подтверждает или отклоняет замечание.
- **Готовые вопросы заказчику.** Противоречия и пропуски оформлены вопросами с вариантами ответа и
  собраны в конце отчёта по адресатам: владельцу продукта, архитектору, руководителю тестирования.
- **Итог для планирования.** «Можно начинать», «можно с условием» или «начинать нельзя» с перечнем
  замечаний-оснований; код выхода тот же — прогон встраивается в CI репозитория с требованиями.

Решения остаются за человеком: агент не выбирает за банк, какое из противоречащих правил верное, и не
заменяет согласование. Процент экономии времени не заявляем — он зависит от документа и ревьюера.

## Как устроено

```
документ ─▶ чтение и проверка входа ─▶ реестр требований (код)
          ─▶ правила без модели ─┐
          ─▶ модель: каждое требование (с контекстом всего документа)
          ─▶ модель: набор — правила, приёмка, интерфейс и данные, свободный проход
                                 └▶ проверка цитат ─▶ справочник серьёзности ─▶ склейка дублей
                                     ─▶ паспорт, сводка, итог (код) ─▶ отчёт
```

Принципы:

- **Модель классифицирует, код решает.** Модель называет тип дефекта из закрытого списка, приводит
  дословные цитаты и оценивает последствие. Номера строк, серьёзность, пункт стандарта и итог ставит код.
- **Цитата не найдена в документе — замечания нет.** Цитаты ищутся точным вхождением после нормализации
  пробелов, переносов, кавычек и Markdown-разметки; строки таблиц — по соседним ячейкам.
- **Блокер — только для бизнес-поведения.** Расхождения уровня протокола не выше «критичного».
- **Противоречие — вопрос заказчику, а не выбор за него.**
- **Без подгонки под документ.** В коде, промптах и тестах нет строк выданного ТЗ; это проверяет тест
  (ниже). Текст документа подаётся модели как данные: инструкции внутри документа не исполняются.

```
src/reqcheck/
  cli.py, pipeline.py        запуск и порядок этапов
  models.py, llm.py          контракты данных и ответов модели
  llm_client.py, llm_providers.py, llm_cache.py
                             Gemini / Claude / OpenAI-совместимый, повторы, кэш, предохранитель расходов
  prompts.py, prompts_open.py, taxonomy.py
  stages/                    reader (md, docx, pdf), registry, rules, checks, grounding, consolidate,
                             report, render (md, html, pdf)
  profiles/                  профили домена под флагом --profile (bank)
  evalkit.py                 сверка отчёта с золотым набором
eval/baseline.py             контрольный прогон «голая модель»
eval/score.py                eval-команда: «найдено k из n» по золотому набору
```

## Разработка

```bash
uv run pytest
uv run ruff check .
```

Eval-команда прогоняет агента на документе и сверяет отчёт с золотым набором (JSON: пункт и фрагменты
документа, которые отчёт обязан процитировать). Печатает «найдено k из n», пропуски и замечания вне
набора; `--min-recall` делает её гейтом для CI. Формат набора — в `src/reqcheck/evalkit.py`.

```bash
uv run python eval/score.py требования.md золотой_набор.json --min-recall 0.7
uv run python eval/score.py требования.md золотой_набор.json --no-llm      # только правила, бесплатно
```

Тест против подгонки: падает, если в коде, промптах или тестах есть идентификатор, число или фраза из
проверяемого ТЗ. Словарь не хранится в репозитории — строится из документа при запуске:

```bash
REQCHECK_ISSUED_DOC=/путь/к/выданному/ТЗ.md uv run pytest tests/test_no_overfit.py
```
